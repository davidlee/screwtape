## How sync tests drive a fake server

`sync_test` never opens a socket. One case is `sync_fixture.run(store, spec)` (`sync_fixture.gleam:321`):

1. **The script.** `Spec` (`sync_fixture.gleam:54`) holds `script: List(fixture_send.Step)`, `bounds: sync.Bounds`, `max_objects_in_get`, `is_read_only`, `max_total_bytes`, `now`. `spec`:67 defaults to `bounds(Some(100))`, 1000 objects/get, read-only, 1 MB, and a `now` half a second past `now_text` to catch a missing truncation (`:93`).
2. **Queueing/matching.** `run` prepends the session reply — `fixture_send.Step(http.Get, ok(session_body(spec)))` (`sync_fixture.gleam:322-325`) — to the script and starts `fixture_send.start`:79. `loop` (`fixture_send.gleam:161-190`) pops **one step per HTTP request, by position**; an `Expect(method, reply)` additionally requires the request be a POST whose *first* `methodCalls` entry names that method (`matches`:190-200). A mismatch or an over-run request is answered `500` and recorded `matched: False` (`:172-188`), which the client maps to `Http("status_500")`.
3. **Building replies.** Step builders are one-liners over `jmap_fixture`: `mailboxes`/`opening`/`opening_with`:116,121,137 wrap `jmap_fixture.opening_entries`/`responses`; `page`/`page_with`:143,153 wrap `email_query_response`; `emails`/`threads`:174,185 wrap the get responses; `fetch`/`fetch_chunked`:203,210 compose `Email/get` + `Thread/get` chunks with `es-1…`, `ts-1…` states from `numbered`:222.
4. **Recording.** `Recorded` (`fixture_send.gleam:52`) keeps method, URL, headers, body and the cap the caller passed. `Run` (`sync_fixture.gleam:285`) keeps `calls` = the first call of each request (`recorded_calls`:126), `requests` = every POST's full call list (`calls_of`:139), `unmatched` = `unmatched_count`:145, and `before`/`after` dumps.
5. **Asserting the wire.** `expect_calls(run, methods(script))` (`sync_fixture.gleam:362`) compares the whole ordered call-name list *and* demands `unmatched == 0`; `methods`/`list.map(script, method_of)`:253. Finer assertions: `opening_calls`:396, `calls_of`:402, `int_argument`:408, `positions`/`limits`:421,430, `id_lists`:436, `filter_mailboxes`:441.
6. **Inspecting the store.** `store_dump.dump` is taken on the path with the writer still open, before and after (`sync_fixture.gleam:333-337`); `expect_unchanged`:372 requires byte-equal dumps incl. `user_version` and then *commits a probe write* to prove no transaction leaked. Row-level checks go through `rows`/`count`:454,466 and the test-local decoders `message_states`/`type_states`/`query_state_row`/`sync_row` (`sync_test.gleam:123,135,143,168`); `summary(run)`:388 reads the `Ok` summary.

**For M2 (Email/changes)**, exactly this needs extending:

- `request.Method` has no `Email/changes` variant (`src/screwtape/jmap/request.gleam:41-56`). Because `Expect` matching (`fixture_send.gleam:190-200`), `methods`/`expect_calls` (`sync_fixture.gleam:253,362`) and `calls_of`:402 all derive from `request.method_name`, adding the variant makes the whole matching/assertion stack work with no test-support edit.
- `jmap_fixture` needs a `changes_response(old_state, new_state, has_more_changes, created, updated, destroyed)` next to `email_query_response`:127 (`method_response(request.method_name(EmailChanges), json.object([...]))`), and an `error`-flavoured one built from the existing `error_entry`:358 (`cannotCalculateChanges` is already a recognised method problem type, `src/screwtape/jmap/decode.gleam:69`) — no new fixture type needed.
- **Caution**: `jmap_fixture.opening_entries`:327-346 zips `request.opening(...)`'s call names against a hard-coded 3-element argument list. If M2 adds a call to `request.opening`, `list.zip` silently truncates and every existing scripted opening answer becomes short → `Decode("methodResponses")`. If `Email/changes` is its own request (it must be, since `sinceState` comes from the store), the fixture is unaffected — but the 4th argument would have to be added to `opening_entries` and to `sync_fixture.opening`/`opening_with`:121,137.
- `sync_fixture` needs: `changes(created, updated, destroyed, old_state, new_state, has_more_changes) -> Step` and a `changes_error(type_) -> Step` beside `page`/`emails`:143,174; a `string_argument(call, name)` beside `int_argument`:408 to assert `sinceState` (an `Int`-only accessor today) — `maxChanges` already works via `int_argument`; and `fetch`/`fetch_chunked`:203,210 reused for the `created`/`updated` ids. `destroyed` is asserted through the store, i.e. `rows`/`count`:454,466 or `sync_test.message_ids`:131, not through `id_lists`:436 (that reads request arguments).
- A `type_state(store, "Email")` accessor next to `rows`:454 so a case can assert the run sent back the state a previous run stored — today that lives privately in `sync_test.type_states`:135.
- If `sync.Bounds` grows (e.g. a `max_changes` or an incremental policy flag), only `sync_fixture.bounds`:80 needs the new field: the test-side rewrites use record update (`sync_test.gleam:58,62`).

**A second run against a pre-populated store is already easy** — `with_store(None)` then `run(store, spec)` twice on the same open writer is exactly what `repeated_run_identical_dump_test` (`sync_test.gleam:782-794`) and `window_leaver_rows_removed_test` (`:796-814`) do, and `Run.before/after` give both sides.
